# Offline recording

Updated 16 October 2026. Hardening and theatre-register changes are published to the fictional-data review (see deployment.md). Offline recording is required and a local implementation now exists. The original online-only proposal is superseded.

## Implemented behaviour

Sign in online once per account/browser/origin with your account password and visit the hospital departments to prepare their records. Login has one **Open workspace** action. After sign-in, a remembered device session restores the encrypted workspace across reloads and browser restarts until explicit logout or three days of inactivity. Restoration checks current identity/permissions when connected and uses prepared data during outages. The user does not select an offline mode. Use the built PWA on port 4173 for offline reloads; the Vite development server does not install a service worker. Unseen records and first-time sign-in require connectivity.

| Action | Current behaviour |
| --- | --- |
| View prepared cases | Encrypted department subset, with server refresh time; local search only. |
| Register a patient/case; edit demographics or case notes; change clinical priority/readiness/hold | When connected, send to the server first and show Synced only after acknowledgement. If the connection or server is temporarily unavailable, save a role-authorised durable pending operation; the server checks current permission, department scope and version on replay. |
| Record theatre entry, completion or cancellation | When connected, send to the server first. During an outage, save an authorised operation locally (start/end for recorders; cancellation only for doctors/write admins), preserving actual event and recording times. |
| Create/edit a theatre-register entry (local preview) | Server-first; fall back to the same encrypted outbox. Draft/verified permissions and entry versions are checked again on replay. Latest 500 saved entries plus prepared completed bookings are available offline; period reports require connectivity. |
| Create sessions or book shared slots | Online server confirmation required. An uncertain response can be retried with the same submitted request while its form remains open. Refresh after closing an uncertain form to inspect server state. |
| Admin configuration and staff account/access changes | Online-only; automatic invitation email delivery, exports and advanced outcome/delay recording remain unimplemented. |

Connected updates go to the hospital API before the local working copy changes. Only an API acknowledgement is labelled **Synced**. A validation, permission or version-conflict response is shown immediately and is not placed into an automatic retry loop. A lost response, connection failure, rate limit or temporary server failure falls back to the encrypted outbox using the same operation ID, so replay is idempotent even if the server accepted the first request.

An offline entry is **Saved on this device** only after the IndexedDB write completes. It is shared only after server acknowledgement. Pending activity is projected into the local case view; dashboard metrics remain based on the last accepted server snapshot. One invalid queued edit, including a diagnosis whose WHO ICD-10 code cannot be applied, is skipped for that projection and left in the outbox. The browser logs that queue item’s id and operation type, and not the patient details. The prepared workspace and the other queued edits still open. On network loss, the queue survives reload and normal tab/browser closure; an unexpired session recovers it automatically. **Explicit Log out deletes that account’s entire device vault and unsynced work**, as Dylan requested. Work that has only been saved on one device is unavailable on another device until the server accepts it. Queued operations replay in sequence, and a later update queues behind earlier pending work to preserve that order. Bookings are never presented as confirmed from an offline local projection.

Acknowledgement and outbox removal now share one encrypted write. New API receipts include authoritative changed records, including the actual existing patient identity when registration links a further case. These update all relevant prepared copies by version; old receipts still have a compatible projection fallback. If saving the acknowledgement fails, the original outbox remains and the same request can replay. A read started before or during a mutation cannot overwrite the acknowledged snapshot. Dashboard metrics still reflect the last fetched server report, not optimistic edits.

All operation forms retain their submitted ID/payload after an uncertain result, including when both a server response and durable fallback fail. Definitive validation/permission/conflict failures unlock editing; rate limits retain identity. HTML/truncated responses preserve HTTP denial versus retry classification. Confirmed bookings/sessions do not become failed saves merely because their follow-up refresh fails. Temporary API/provider errors allow a prepared, unexpired password login to fall back to its existing encrypted workspace; invalid/revoked identities do not.

Browser persistent-storage permission is requested as a best-effort eviction safeguard after saving the encrypted vault. Its answer does not block sign-in, and denial does not mean the IndexedDB write failed. Local storage can still be removed by the user/browser; this is not a loss-proof storage guarantee.

## Local protection and lifetime

`apps/web/vault.ts` stores one encrypted vault row per hashed normalised staff email. Hospital/department workspaces and operations live inside the ciphertext, not plaintext indexes. AES-256-GCM uses a fresh 96-bit IV for each write and binds the account identifier as authenticated data. PBKDF2-SHA-256 (310,000 iterations and random salt) derives a non-exportable key from the account password after Firebase verifies online sign-in. The password and raw key bytes are never stored. To support Dylan’s persistent-session requirement, IndexedDB structured-clones the non-extractable CryptoKey in a separate device-session row, alongside the account UID, vault ID and last activity time. The browser can therefore decrypt while that session remains remembered; encryption is not a password barrier while signed in. Password strength follows the account policy; there is no separate local-passphrase requirement. This is a synthetic pilot implementation, not a reviewed institutional device-encryption policy.

A browser Web Lock still permits only one workspace tab per origin, preventing whole-vault overwrites. A blocked tab does not alter the working tab’s shared authentication. Log out immediately disables new saves/replay, waits for in-flight durable writes, atomically deletes that account’s local ciphertext and remembered key, signs out of Firebase, then releases the tab lease. Late saves cannot recreate the deleted vault. Storage/sign-out failures display Retry log out instead of claiming completion. Firebase local persistence, the remembered UID and API owner checks prevent replay under another account. An online refresh removes revoked workspaces; saved pending work is retained for its original owner, with details restricted to current local grants. The server always checks fresh membership.

The old 15-minute lock and fixed 24-hour offline lease are superseded. The session expires after **72 elapsed hours without user activity**, including while the browser is closed. Pointer/keyboard/scroll/touch activity and returning to a visible app renew activity; background refresh and automatic sync do not. Startup, focus, the foreground timer and API/mutation guards check expiry before renewing it. Expiry removes the remembered key and signs out; encrypted pending work remains for a later password sign-in. Explicit logout deletes it. Immediate remote revocation is impossible while disconnected. Online sign-in never asks for a second secret. If the account password decrypts the old vault, pending operations migrate directly. Otherwise the full original encrypted row (ciphertext, salt, IV and authenticated account identifier) is preserved inside the new encrypted vault as a `savedWork` backup. A single atomic IndexedDB write stores both the backup and the new account-password workspace before opening. Failed writes leave the original row untouched. This applies to legacy passphrases and changed account passwords; offline unlock never creates a replacement after a wrong password.

Dylan explicitly removed pre-release migration notices and all old-secret recovery flows on 4 October. The banner, recovery form, recovery state action, decryption/merge helper and obsolete help styles are deleted. Existing `savedWork` development archives remain encrypted in storage and survive normal sign-in/saves without a UI or replay, but explicit logout now deletes them with the account vault. Saved activity describes the **current workspace** only. This retention avoids deleting old development data during a UI cleanup; it is not a production password-recovery feature. A forgotten encryption secret still cannot decrypt old unsynced data. Browser storage remains local and there is no separate archive export or supported app downgrade.

Persistent browser storage is requested where available. Quota errors propagate before local success. Storage may be cleared, evicted or lost; this app cannot promise loss-proof offline records. Encryption also does not protect an unlocked app from malicious same-origin scripts. [Web Crypto](https://developer.mozilla.org/en-US/docs/Web/API/Web_Crypto_API), [browser storage](https://developer.mozilla.org/en-US/docs/Web/API/Storage_API/Storage_quotas_and_eviction_criteria), [Dexie](https://dexie.org/docs).

## Replay and conflict handling

The local theatre extension also carries an entry version and entry ID. Dependent register edits queue behind earlier edits of the same entry. Acknowledgement snapshots merge the authoritative entry into prepared copies in the same durable write that removes the pending operation. Draft/verification permissions are rechecked on replay. Register conflict review preserves the proposal; there is no automatic merge.

Each operation has a UUID, hospital/department scope, payload, base case version, event time and recording time. Client order preserves case dependencies. API transactions atomically write the transition, actor-attributed audit event, and actor/payload-bound idempotency receipt with a server receipt time. The current role and department are checked even for receipt replays. A lost response can therefore be retried without a second effect.

Foreground replay runs when the workspace opens, on reconnect, window focus, return to a visible tab, manual sync and a 30-second visible-page interval. Network/temporary errors retain pending operations. Version conflicts and validation/permission rejections from replay remain in Saved activity. A failed case operation also marks its dependent queued edits for review. Saved values can be compared with the current case, or kept locally as reviewed without applying them. Applying a revised proposal requires a new permitted edit; there is no silent overwrite, automatic patient merge or one-click rebase. Resolved entries remain encrypted locally.

The Firestore client cache is not used for clinical records: its last-write-wins document sync cannot enforce this custom API operation protocol. [Firestore offline behaviour](https://firebase.google.com/docs/firestore/manage-data/enable-offline).

The service worker caches only static app assets, including fonts/icons. API responses are `no-store`. App updates have an explicit notice; save any open form before updating. A signed-out, closed or suspended app does not upload pending work. A request already sent before logout may still complete at the server; logout cannot undo an accepted change. Background Sync is not relied on. [Background Sync support](https://developer.mozilla.org/en-US/docs/Web/API/Background_Synchronization_API).

## Verified and still required

Verified in Chromium: a connected case-note update went directly to the server and left no pending entry; a disconnected edit was durably marked pending and synced automatically on reconnect; offline registration → offline reload → unlock → recovered pending entry → reconnect → acknowledgement; clerk entry/completion queued offline and replayed in order; second-tab exclusion; lock/reopen; a competing priority update surfaced as Needs review while preserving the offline proposal. API integration checks cover receipt replay, stale versions, semantic duplicate completion and current membership revocation. See [verification](verification.md).

Still required before real-device/hospital use: physical Android/iOS and Safari/Firefox; real-browser storage-full/eviction testing (atomic migration write failure is unit-tested); browser restart and extended outage/device clock tests; forgotten-password data recovery and stranded-record procedures; future schema migrations with pending entries (legacy key migration is unit-tested); a supported retention/device enrolment policy; stronger bounded retry/backoff and production-scale preparation/pagination. The current UI prepares 250 prioritised cases plus all cases referenced by returned bookings per department and uses the user-confirmed three-day inactivity policy.


Implementation references: [Firebase Auth persistence](https://firebase.google.com/docs/auth/web/auth-state-persistence), [persisting CryptoKey in IndexedDB](https://developer.mozilla.org/en-US/docs/Web/API/CryptoKey). See [verification](verification.md) for the current logout/session checks.
